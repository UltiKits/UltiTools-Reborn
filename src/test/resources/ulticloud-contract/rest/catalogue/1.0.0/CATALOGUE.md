# UltiCloud catalogue REST contract 1.0.0

Generated by `pnpm --filter @ulticloud/contracts generate:catalogue` from the REST contracts in `packages/contracts/src/rest/`. Do not edit by hand.

This directory holds the JSON Schemas (Draft 2020-12) and golden fixtures of the public catalogue routes the framework uses (`/upm` and the update check). Every schema is self-contained, uses no `format` keyword and only anchored patterns from the portable regex subset of the agent protocol export, so a validator without format assertions (for example networknt json-schema-validator with JDK regex) reaches the same verdict as the server.

## Operations

| Operation | Route | Contract id |
|---|---|---|
| `modulesList` | `GET /v1/catalogue/modules` | `catalogue.modules.list` |
| `moduleGet` | `GET /v1/catalogue/modules/:moduleRef` | `catalogue.modules.get` |
| `versionsList` | `GET /v1/catalogue/modules/:moduleRef/versions` | `catalogue.modules.versions.list` |
| `versionGet` | `GET /v1/catalogue/modules/:moduleRef/versions/:version` | `catalogue.modules.versions.get` |
| `versionDownload` | `GET /v1/catalogue/modules/:moduleRef/versions/:version/download` | `catalogue.modules.versions.download` |
| `framework` | `GET /v1/catalogue/framework` | `catalogue.framework` |
| `categories` | `GET /v1/catalogue/categories` | `catalogue.categories` |
| `tags` | `GET /v1/catalogue/tags` | `catalogue.tags` |

Schema files are `schemas/<operation>.<part>[.<status>].schema.json`, where `part` is `query` (the decoded query string), `response` (success body), `error` (error envelope by HTTP status) or `headers` (response headers). `versionDownload` has no response body schema: its 200 body is the JAR itself.

Fixtures are `fixtures/<operation>/<part>/{valid,invalid}/<name>.json`. A valid fixture is the JSON value itself; an invalid fixture is `{ "expect": "invalid", "why": "…", "body": … }`. A `<status>-` name prefix (for example `404-not-found.json`) selects that status's schema; otherwise any schema of the part applies.

## Parameters

| Route | Parameter | Type and default | Meaning |
|---|---|---|---|
| `modulesList` | `q` | string, at most 100, optional | Case-insensitive (ASCII) substring match on name, identifier and short description |
| | `category` | positive integer category id, optional | Only that category; an unknown id gives an empty page, not 404 |
| | `tag` | tag name 1..24, optional | Only modules with that tag, compared case-insensitively; unknown gives an empty page |
| | `sort` | `popular` \| `newest` \| `updated` \| `name`, default `popular` | Ordering, with the id as a stable tie-breaker |
| all paged routes | `page`, `pageSize` | `page` ≥ 1, default 1; `pageSize` 1..100, default 20 | A page past the end has empty `items` and the real `total` |
| `versionsList` | `apiLevel` | integer 1..99999, optional | Only versions with `apiLevel` ≤ this value (the framework's own API level) |
| | `minApiLevel` | integer 1..99999, optional | Only versions with `apiLevel` ≥ this value (the framework's lower bound, 630 for 6.3.x) |
| | `includeWithdrawn` | `"true"` \| `"false"`, default `"false"` | `"true"` also lists withdrawn versions, read-only; the framework does not send it |
| `tags` | `q` | string, at most 100, optional | Case-insensitive substring match on the tag name; at most 10 results |

`apiLevel` and `minApiLevel` are independent and both optional. When either is given, only versions whose `apiLevel` is non-null and inside the range are returned; `minApiLevel > apiLevel` gives an empty page, not an error.

Query fixtures and `query` schemas describe the query string **after decoding**: integer parameters are JSON numbers and enumerations are strings. In the URL, send integers as decimal strings (`?apiLevel=631&minApiLevel=630`); the server decodes them before validation. A key given twice, or a key that is not declared, is rejected with 422 `validation_failed`. Do not enable type coercion in the validator: the fixtures are already decoded.

## moduleRef

`:moduleRef` is either a module's public id (a ULID, 26 upper-case Crockford base32 characters) or its identifier (lower-case letter first, segments separated by a single `.` or `-`, 1..64 characters). The two grammars do not overlap. URLs in responses always use the identifier.

## URLs

Every URL in a response is an absolute `https:` URL (at most 2048 characters). Download URLs currently have the shape `<API origin>/v1/catalogue/modules/<identifier>/versions/<version>/download`, and icons stored by UltiCloud `<API origin>/v1/catalogue/modules/<identifier>/icon`; an icon may also be an external `https:` URL. The shapes are descriptive only: callers use the URL as an opaque `https:` address and must not build or parse it. `framework.downloadUrl` points at the JAR on Maven Central.

## apiLevel null

Each version carries `apiLevel`: the integer `api-version` declared in the module's `plugin.yml`, or `null` when it is unknown (for example versions migrated from before 6.3.0). A `null` level never matches a level filter, so a framework that sends `apiLevel` or `minApiLevel` never receives such versions.

## Withdrawn versions

`download` is a discriminated union on `kind`: `public` (has `url`), `license_required` (paid modules, a later phase; not produced yet) and `withdrawn` (has `withdrawnAt`, no URL). Withdrawn versions appear only in `versionsList` with `includeWithdrawn=true`; the framework does not send that parameter and never receives them. Treat every `kind` other than `public` as not downloadable. `versionGet` and `versionDownload` answer 404 for a withdrawn version. A module whose versions are all withdrawn still has a detail page (`latest: null`) but is not listed or searched.

## 404

404 `not_found` means the same thing everywhere: the module or version does not exist, is not published, or (for a version) is withdrawn. No route distinguishes these cases. A download for anything other than a published, public version is always 404.

## Sync

Sync only versions listed in `../RELEASES.json`; a listed version never changes (its `MANIFEST.json` SHA-256 is frozen there). Copy the whole version directory, then verify every file against `MANIFEST.json`. Record `{ contractVersion, manifestSha256, sourceCommit }` in the framework's lock file, as for the agent protocol.
