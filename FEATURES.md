# UltiTools-API — Feature Inventory

This document catalogues operator-, player- and module-author-visible functions, commands, content items and
configuration keys in this repository, as read directly from source. It is an internal reference
for UAT execution and issue reconciliation — the public description of these features lives on
<https://doc.ultikits.com/>. Update this file in the same pull request as any feature change.

## Conventions

- **ID grammar:** `<repo-slug>.<area>.<action>`, dot-separated, every segment lowercase ASCII
  drawn from `[a-z0-9-]`. `<repo-slug>` is the repository name lowercased with no separators —
  `ultitools` here, `ultichat`, `ultiessentials`, and `ultitools-example` for
  `UltiTools-External-Example`. `<area>` is the feature section's slug. `<action>` is the verb.
Two shapes exceed three segments. An aspect row adds one more `[a-z0-9-]`
  segment, `<repo-slug>.<area>.<feature>.<aspect>`, for one behaviour of a feature that has its
  own UAT row (`ultitools.cloud.outbox.persist-restart`, `ultitools.upm.install.sha256`); the
  `.neg-<slug>` suffix stays checklist-only. A `config` row is the other shape, and the only one
  exempt from the lowercase-ASCII rule for its key-path suffix:
  `<repo-slug>.config.<file-stem>.<yml key path>`, the key path keeping its own dots and its own
  casing verbatim from the yml file (`config.yml` itself uses camelCase for several keys, e.g.
  `maximumPoolSize`) — a config ID is a citation of the key, not a re-derived slug, so lowercasing
  it would make it un-greppable against its own source line. An ID changes only when the feature's
  identity changes, never on rewording. IDs are unique within a
  repository.
- **Kind**, exactly these eight values: `command`, `config`, `event`, `gui`, `scheduled`,
  `placeholder`, `persistence`, `gate`. Each maps one-to-one onto a reconciliation-table line.
- **Tier**, exactly three: `player`, `admin`, `internal`. Judged from what the feature is for,
  not from whether it carries a permission string — most command executors in this repository
  carry one, so judging by the string alone would make nearly everything `admin`.
- **Manual**, exactly three: `detailed`, `brief`, `none`.
- **Target**, exactly four: `player`, `console`, `both`, or `n/a` — the first three read straight
  off `@CmdTarget` for a `command` row; it is a property, not a tier. `n/a` is for every other
  Kind (`config`, `event`, `gate`, `gui`, `persistence`, `scheduled`, `placeholder`) — the concept
  of "who this targets" does not apply to a config key or a background task the way it applies to
  a command.
- **Permission:** the literal node string, `none`, or `n/a`, each optionally suffixed with the
  literal text `(requireOp=true)` (preceded by one space) when the row's class-level
  `@CmdExecutor` carries that flag —
  the suffix augments whichever of the three base values applies; it is not a fourth value, and a
  row without it means its class's `requireOp` is `false` (or the row's Kind has no such class at
  all). An empty permission node does not itself restrict access:
  `CommandAccess#permission` checks the OP flag separately from the permission node.
  Every `/ul`, `/upm` and `/ulticloud` mapping in this repository has the class-level
  `@CmdExecutor(requireOp = true)` flag; the console-only `/ulticloud` sender rule is separate.
  The suffix makes the OP requirement visible without consulting the class declaration.
  `n/a` is for
  every Kind that is not `command` — a config key or a scheduled task has no permission node to
  declare in the first place, which is a different fact from a command that declares `none`
  deliberately.
- **Source:** `ClassName#member` — the class and member that actually reads or applies the
  feature — for every Kind, `config` included: config rows below cite the reading
  member (e.g. `JsonStore#initScheduler`, `UltiTools#initDataStore`), not the resource path,
  because the resource path is already stated in the How-to-reach column and does not by itself
  say what code does with the key. `ClassName#member` for a `config` row need not be an
  annotation site — most config keys in this repository are read directly via Bukkit's
  `FileConfiguration`, with no `@ConfigEntity`/`@ConfigEntry` binding at all (see the
  `## Configuration` section's own zero-`@ConfigEntity` note).
- **Row order:** by section, then by ID ascending within the section.
- **No manual prose:** no troubleshooting column, no explanatory paragraphs, no draft page text.
  A hazard noticed while reading becomes a negative checklist row, not a note here.

### Reconciliation command family

The canonical form for counting an annotation site across this repository's real sources:

```bash
find <repo-root> -path '*/src/main/java/*' -name '*.java' -not -path '*/target/*' \
  -not -path '*/.worktrees/*' -print0 | xargs -0 grep -nE '^[[:space:]]*@AnnotationName\b' | wc -l
```

This form defeats three measured traps, each of which produces a wrong-but-plausible number
rather than an error:

1. **Multi-root repositories** — UltiBot's sources live under `ultibot-api/`, `ultibot-core/`
   and `ultibot-v1_21_R1/`, so a naive `<repo>/src/main/java` glob returns 0 for it, silently.
2. **Git worktrees and build output** — UltiEconomy carries
   `.worktrees/economy-v2/src/main/java`, so a `find` without the `-not -path` exclusions above
   reports 48 `@CmdMapping` sites where the real number is 24.
3. **Javadoc and string literals** — requiring the annotation to start its own line (the
   `^[[:space:]]*@` anchor) counts declaration sites instead of examples and warning strings.

**Positive control (7.0):** `/ul` = 4, `/upm` = 10, `/ulticloud` = 5 (19 `@CmdMapping` sites).
These are actual annotation sites: `UltiToolsCommands.java:60,77,137,142`;
`PluginInstallCommands.java:60,126,132,138,144,180,185,211,344,421`;
`CloudLoginCommand.java:53,72,84,129,146`. Inventory rows additionally describe unannotated
framework replies, aliases and behavioural aspects, and panel requests need no command annotation. One
more trap of the same kind: run from inside a git worktree (a checkout under `.worktrees/`), an
absolute search root itself matches `-not -path '*/.worktrees/*'` and the count is 0, so use `.`
as the root there.

## /ul — framework administration

`UltiToolsCommands` — class-level `@CmdExecutor(alias = {"ul", "ultitools", "ulti"}, requireOp =
true)`, `@CmdTarget(BOTH)`. There are four live `@CmdMapping` sites in `UltiToolsCommands.java`:
lines 60, 77, 137 and 142 (`reload`, `reload <name>`, `help`, `list`).
`reload` invokes `UltiToolsCommands#reloadAll`, which replies with the reload summary;
`#reloadPlugins` is retained without a mapping (#509).
The explicit `help` mapping counts as one site.
**6.x history:** the old `onCommand`
short-circuited `help` before the string matcher. **7.0:** the explicit `help` mapping is a live
Brigadier leaf, invokes `UltiToolsCommands#help`, and that method calls `#handleHelp`. Commands
without an explicit help mapping receive a synthesized gated-help leaf instead.

## /upm — plugin management

`PluginInstallCommands` — class-level `@CmdExecutor(alias = "upm", requireOp = true)`,
`@CmdTarget(BOTH)`. `PluginInstallCommands.java` declares ten live `@CmdMapping` sites:
`list <page>`, `list`, `install <plugin> <version>`, `install <plugin>`, `versions <plugin>`,
`uninstall <plugin>`, `pending`, `revoke <module>`, `check`, and `update <plugin>`.
Several checklist probes exercise different outcomes of the same command.
`/upm help` (also the bare `/upm` with no arguments) is
reachable and operator-visible, but has no `@CmdMapping` site. In 7.0 the compiler synthesizes a
`help` leaf that invokes gated `PluginInstallCommands#handleHelp`; the bare root retains the
unknown-command message followed by gated help. The old `onCommand` short-circuit is **6.x
history**, not the current registration mechanism. `/ul help` is an explicit live mapping.
The synthesized help leaf adds no annotation site.
`update <plugin>` is one `@CmdMapping` site whose method,
`PluginInstallCommands#updatePlugin`, branches on whether the argument equals
`all` ignoring case — two independently observable behaviors
(`ultitools.upm.update` for one named module; `ultitools.upm.update-all` for
`PluginInstallCommands#updateAllPlugins`'s own iteration and partial-failure accounting) sharing
one annotation site, split into two rows here so the checklist can cite a real feature ID for
each. `ultitools.upm.install.sha256` and `ultitools.upm.update-check.v2` are
`gate` aspect rows (Conventions, ID grammar), not commands — the
verified-download check and protocol v2 catalogue used by catalogue-backed `/upm` operations
and the startup update check.

## /ulticloud — cloud authentication

`CloudLoginCommand` — class-level `@CmdExecutor(alias = "ulticloud", requireOp = true)`,
`@CmdTarget(CONSOLE)`. The five current `@CmdMapping` sites are `CloudLoginCommand.java:53,72,84,129,146`
(`login`, `login <code>`, `logout`, `status`, and `reconnect`). This section carries six command rows, not five:
`/ulticloud help` reaches
`CloudLoginCommand#handleHelp` through the synthesized gated-help Brigadier leaf in 7.0, with no
`@CmdMapping` site of its own. Bare `/ulticloud` prints the unknown-command reply first, then the same gated help.
The old `BaseCommandExecutor.onCommand` short-circuit is 6.x history; 7.0 has 19 `@CmdMapping` sites across the three framework command classes.
The other rows are not commands. `ultitools.ulticloud.credential-migration` and
`ultitools.ulticloud.legacy-token-cleanup` are rules of the credential store; the `gate` rows are what the
protocol v2 connection (as of 6.3.1) does by itself when UltiCloud refuses or closes it, and
`ultitools.ulticloud.v1-silent` is the absence of every protocol v1 path. The 6.3.0 row
`ultitools.ulticloud.request-helper` is retired: protocol 2.0.0 removed the magic-link endpoints it sent to,
`UltiCloudRequests` refused every call without a request from 6.3.1 and was removed in 6.4.0, and player links moved to
`ultitools.cloud.player-link`.

(`ultitools.listener.placeholderapi-bridge`, `ultitools.listener.update-notify`) are Bukkit join

never runs `ComponentScanner`/`ListenerManager` over itself — only a per-plugin

causes registration here. Both join listeners above are registered via direct Bukkit event
registration; boot also directly registers the pending-changes and cloud-outbox listeners.

annotation at all and reconcile against nothing, because module discovery, module load-order (in
either its resolved or legacy-bypass form) and the update check have no annotation-based
instrument in this codebase. The last three
(`ultitools.boot.deferred-removal`, `ultitools.boot.module-update-apply`,
`ultitools.boot.module-update-observe`) are steps of
startup itself — before the module class loader is built (`ModuleClassPath#moduleClassPath`),
and after module loading returns (`UltiTools` calls `ModuleFileTransactions#observeAfterLoad`) —

## Module lifecycle registries

Which copy of a module owns what it registers in the framework's three name-keyed registries — panel responders
(`PanelResponderRegistry`), EventBus subscriptions and handlers, tab completers — when a newer copy of a loaded module
replaces it, or when it registers after it loaded (6.3.0, #562). A newer copy replaces a loaded one only when code calls
`PluginManager#register(UltiToolsPlugin)` with a newer instance; no operator command does (duplicate JARs declaring the same main class are skipped at the
scan, `/ul reload` reloads configuration and message overrides only, and staged module updates need a restart), so these rows are unit-pinned.

## Module configuration persistence

What the framework writes to a module's `@ConfigEntity` file (`plugins/UltiTools/pluginConfig/<module>/...`), and when
(6.3.0). The contract is the maintainer's rule of 2026-10-04: configuration an operator wrote is never overwritten
automatically. Every write goes through one write gate that owns named keys and keeps every other byte, or writes nothing
with a diagnostic on refusal; the framework writes no entity configuration at server stop, unload or replacement.
`UltiTools#onDisable` and the module lifecycle report unsaved changes through `ConfigManager` without saving them. See `COMPATIBILITY.md`, "The write contract".
These rows use the three-segment `ultitools.config.<action>` form with
Kind `persistence`; they are not `config`-Kind key rows, which always have four or more segments
(`ultitools.config.<file-stem>.<key path>`). The protected-file state is reachable through
module reload commands as of 6.3.0: failed init and reload both protect the original file. The
framework's own `plugins/UltiTools/config.yml` is not a `@ConfigEntity` (see Configuration); its start-up migration
inserts missing keys through the same gate and it is not written at stop.

Retired for 6.3.1: `ultitools.config.panel-map-entry` (protocol v2's `config.update` edits only typed settings; a map leaf is refused per key, `ultitools.config.panel-map-entry-server`).
