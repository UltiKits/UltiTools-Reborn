# 6.3.0 Removal Records

Behavioural records for the symbols this milestone actually deletes, one `### Recorded instance`
section per removal (or removal-adjacent binary break, see the last entry). Created by plan
07-13 (GEN-04, first cluster of type removals). Later Phase 7 plans append their own removals here
rather than duplicating this file.

Format: what was removed, its replacement, and — per D-19's escalation (plan 07-04) — exactly what
a downstream author sees if their module JAR was compiled against the old symbol and never
recompiled: one `SEVERE` line at module scan, naming the module and the skipped class, pointing at
`COMPATIBILITY.md`. The module still loads (skip-and-continue is unchanged), only the affected
class is skipped.

### Recorded instance: the `VersionWrapper` cluster and all three `getVersionWrapper()` accessors are gone (GEN-04, 6.3.0)

`interfaces.VersionWrapper` (interface, 14 default methods), `interfaces.impl.DefaultVersionWrapper`
(its implementation), and all three accessors that returned one —
`UltiTools#getVersionWrapper()`, `abstracts.UltiToolsPlugin#getVersionWrapper()` (static), and
`context.UltiToolsBean#getVersionWrapper()` (the `@Bean`-registered one issue #213 flagged as
missing from earlier removal-list drafts) — are deleted, along with `UltiTools`'s private
`versionWrapper` backing field and its bootstrap-step-5 `new DefaultVersionWrapper()` construction.

Replacement: `utils.XVersionUtils`, a strict superset — every production caller in this framework
had already migrated to it before this plan started (07-13-PLAN.md Task 1 measured zero `src/main`
callers of the accessor cluster outside its own declaration).

Deprecated since 6.2.0 (interface/accessors) with `forRemoval = true`; the deprecation window ran
its course before this removal.

**What an un-recompiled downstream JAR sees.** A module class that calls
`ultiTools.getVersionWrapper()`, `UltiToolsPlugin.getVersionWrapper()`, or references
`VersionWrapper`/`DefaultVersionWrapper` by name fails to load with
`NoClassDefFoundError: com/ultikits/ultitools/interfaces/VersionWrapper` (or
`.../UltiTools$getVersionWrapper` for the accessor case — the missing symbol names the removed
type or method). `ComponentScanner`/`PluginManager`'s `catch (ClassNotFoundException |
LinkageError e)` sites (`NoClassDefFoundError` is a `LinkageError`) turn this into one `SEVERE`
`ModuleScanDiagnostics` summary naming the module and the skipped class; the module still loads and
enables (skip-and-continue unchanged, D-19/D-25/D-26). Task 1 measured **zero** binary references
to `VersionWrapper` or `AbstractDataEntity`-family symbols across the six migrated downstream
repositories and, separately for this cluster, zero across all 16 pre-built module JARs on the
local dev server — the strongest evidence available that this failure mode, while real, has no
currently-deployed trigger.

### Recorded instance: `AbstractDataEntity` is gone; `BaseDataEntity` now owns its `id` field directly (GEN-04, 6.3.0)

`abstracts.AbstractDataEntity` is deleted. `abstracts.data.BaseDataEntity<ID>` no longer extends
it — it declares its own `@Column("id") private ID id;` field with direct `getId()`/`setId()`
accessors, replacing the previous `Object`-typed field it inherited and delegated to.

Replacement: `abstracts.data.BaseDataEntity<ID>` (already the framework's current, non-deprecated,
actively-recommended entity base; this removal only changes what it extends, not what a caller
uses). `getDataOperator`'s `<T extends BaseDataEntity<String>>` bound is unaffected — it never
mentioned `AbstractDataEntity`.

Deprecated since 6.2.0 (`@Deprecated(since = "6.2.0", forRemoval = true)`) with a `removeIn 6.3.0`
tag; the deprecation window ran its course.

**JSON storage backend, verified not just reasoned about.** `BaseDataEntity`'s own pre-6.3.0
javadoc explained the `Object`-typed delegation existed specifically to dodge Gson's "declares
multiple JSON fields named 'id'" error, which fires when two classes in one hierarchy both declare
a field mapped to the same JSON key. With `AbstractDataEntity` gone, `BaseDataEntity` is the only
declarer in its own hierarchy, so that collision cannot occur — and `BaseDataEntityTest`'s two JSON
round-trip tests (written RED-first, TDD, before this change landed) confirm a `String`-typed id
survives `Gson.toJson`/`fromJson` unchanged, and that a hand-written legacy-shape JSON file (the
shape a server running the `json` storage backend has on disk today) still deserializes its `id` as
a `String`, not a `Double` or other misdetected type. All three storage backends were checked, not
just JSON: the two relational backends (MySQL/SQLite) share `AbstractRelationalDataOperator`, whose
`buildColumnDefinitions` reads the SQL column type from the `@Column` annotation's `type` attribute
(defaulting to `VARCHAR(255)`, unchanged by this move) rather than from `field.getType()`, so the
DDL is unaffected; its `insert`/`update` complex-value JSON-encoding branch keys off
`BasicTypeUtil.isBasicType(field.getType())`, and neither `Object` (the old declared type) nor
`Serializable` (the new field's generic-erasure type, since `ID extends Serializable`) is in that
basic-type set, so the branch taken is identical before and after.

**Binary-compatibility reality (measured, not assumed).** 11 of 16 real, pre-built, already-deployed
module JARs on the local dev server carry direct constant-pool references to `AbstractDataEntity`
(Task 1's measurement). Disassembly (`javap -v`) of two of them shows this happens through **two
distinct mechanisms**, not one: `Economy-1.0.1.jar`'s `AccountEntity` (and three sibling entity
classes) extend `AbstractDataEntity` **directly** — bypassing `BaseDataEntity` entirely, evidently
compiled before the 6.2.0 `BaseDataEntity` migration — while `UltiEssentials-1.0.0.jar`'s service
classes were compiled against an **older `DataOperator`/`Query` generic bound** that erased to
`AbstractDataEntity` (`DataOperator#insert(AbstractDataEntity)`, `Query#first():AbstractDataEntity`)
rather than today's `BaseDataEntity<String>` bound. Neither mechanism is fixed by this plan's
`BaseDataEntity` change — both predate it and would break on `AbstractDataEntity`'s deletion
regardless of `BaseDataEntity`'s own inheritance.

**What an un-recompiled downstream JAR sees.** Class verification for any class file whose
bytecode references `AbstractDataEntity` — as a superclass, or in a method descriptor such as
`DataOperator#insert(AbstractDataEntity)` — fails to resolve the type, producing
`NoClassDefFoundError: com/ultikits/ultitools/abstracts/AbstractDataEntity` at classloading time.
`ComponentScanner`/`PluginManager`'s skip-and-continue catch sites turn this into one `SEVERE`
`ModuleScanDiagnostics` summary per affected module, naming the module and every skipped class; the
module still loads and enables around the gap. A module whose entity classes extend
`BaseDataEntity` (not `AbstractDataEntity` directly) and whose `DataOperator` usage was compiled
against the current `BaseDataEntity<String>` bound is **unaffected** by this specific removal — its
own class files never reference `AbstractDataEntity`'s name at all.

### Recorded instance: the three framework core commands' superclass changed from `AbstractCommandExecutor` to `BaseCommandExecutor` (GEN-01, 6.3.0)

`commands.CloudLoginCommand`, `commands.PluginInstallCommands`, and `commands.UltiToolsCommands`
now extend `abstracts.command.BaseCommandExecutor` instead of the deprecated
`abstracts.AbstractCommandExecutor` (plan 07-05, commit `4706bff`). `AbstractCommandExecutor`
itself is untouched by this record — it is not deleted, and remains on its own separate removal
schedule; only these three framework-owned command classes' own supertype changed.

**Why this record is here, not in a GEN-04 plan.** This is a GEN-01 change (07-05), not one of
this plan's (07-13, GEN-04) twelve declared symbols. It is recorded here because it was discovered
blocking `mvn -B -o clean verify -DskipTests` during this plan's own Task 3: 07-05 landed after
plan 07-01 made the japicmp gate build-breaking, but 07-05 only ran `mvn -B test` (never `mvn -B -o
clean verify -DskipTests`), so the gate never saw this superclass change until this plan's own
verify run surfaced it. Fixed here under Rule 3 (blocking issue) rather than left for a later
plan to rediscover — every subsequent Phase 7 plan's verify step would otherwise have inherited
the same red build.

Replacement (for any third party that directly subclassed one of these three specific framework
command classes, which is unlikely — they are `public` but not designed as extension points):
none needed for ordinary command development; write new commands against `BaseCommandExecutor`
directly, per this document's Command System section.

**What an un-recompiled downstream JAR sees.** A module class that directly subclasses
`CloudLoginCommand`, `PluginInstallCommands`, or `UltiToolsCommands`, or that performs an
`instanceof AbstractCommandExecutor` check against an instance of one of these three, sees a
runtime type-hierarchy mismatch: no `NoClassDefFoundError` (both `AbstractCommandExecutor` and
`BaseCommandExecutor` still exist), but `instanceof`/casts against the old hierarchy fail silently
rather than throwing a class-load error. No currently-deployed trigger was found in the six
migrated downstream repositories or the 16 pre-built module JARs (none subclass these three
specific framework-owned classes).

### Recorded instance: `PluginManager`'s with-args reflective construction subtree is gone (GEN-04, 6.3.0, same-release exception clause 1)

The seven-argument `manager.PluginManager#register(Class, String, String, List, List, int,
String)` and the private with-args `initializePlugin(ClassLoader, Class, Object...)` overload it
exclusively called are both deleted, along with the two private helper methods that existed only
to serve that call chain — `validateConstructorArgs` and `isSafeParameterType` (neither carried
its own `@Deprecated` annotation; they are ordinary internal cleanup, not separately tracked
removals).

Replacement: `register(UltiToolsPlugin)` — construct the plugin instance yourself. It takes an
already-constructed instance and performs no reflective construction of its own.

**Same-release exception, clause 1 (proven non-functional).** Both removed members carry
`@Deprecated(since = "6.3.0", forRemoval = true)` — zero minor releases have passed since that
annotation first appeared, so the ordinary two-condition removal rule does not apply on its own.
The reproduction clause 1 requires: `SecurityPolicy#isSafeParameterType` matches constructor
argument types by exact runtime-class-name prefix (`java.util.List`, `java.util.ArrayList`, …),
and neither `Arrays.asList(...)`'s actual runtime type (`java.util.Arrays$ArrayList`) nor any
`Collections.*` wrapper type matches any of those prefixes — the `List`-typed `authors` and
`loadAfter` arguments this overload's own signature requires are rejected by the security check
*before* the module's constructor is ever invoked, on every call, on every release since 6.2.0
(Phase 1 D-15, measured). The seven-argument `register(...)` and the with-args `initializePlugin`
have therefore never successfully constructed a plugin on any released version — there is no
working behaviour a deprecation window would protect.

**What an un-recompiled downstream JAR sees.** A connector calling the seven-argument
`register(...)` fails to load with `NoSuchMethodError` at the call site (the method no longer
exists on the class), turned into one `SEVERE` `ModuleScanDiagnostics` summary per D-19; the module
still loads and enables around the gap. No currently-deployed trigger was found — the six migrated
downstream repositories and the 16 pre-built module JARs show zero references to `new
UltiToolsPlugin(String, String, List, List, int, String)` (the six-argument constructor this
overload's only production caller also required), consistent with the overload never having worked
in the first place.

### Recorded instance: `CommandManager`'s deprecated `register(CommandExecutor, ...)` overloads are gone (GEN-04, 6.3.0)

`manager.CommandManager#register(CommandExecutor, String, String, String...)` and
`register(CommandExecutor)` — the two context-free, non-container-managed registration entry
points — are deleted. Both collided on the name `register` with the current, non-deprecated

`registerCoreCommand(CommandExecutor)`, and `registerExternalCommand(...)` — depended on these

not just their public signature. The shared logic is preserved verbatim under a new private
`registerCommandDirect(...)` primitive rather than duplicated or dropped, so `registerCoreCommand`
and external-plugin command registration behave identically before and after this removal.

**What an un-recompiled downstream JAR sees.** A module calling either removed overload directly
fails to load with `NoSuchMethodError` at the call site, turned into one `SEVERE`

currently-deployed trigger was found — zero references across the six migrated downstream
repositories and the 16 pre-built module JARs.

### Recorded instance: `CommandManager.registerAll(UltiToolsPlugin, String)` is gone (GEN-04, 6.3.0)

The two-argument `registerAll(UltiToolsPlugin, String)` — which reflectively scanned
`packageName` and cast every discovered class to the deprecated `AbstractCommandExecutor` — is
deleted. That cast throws `ClassCastException` for any command class written against the current
`BaseCommandExecutor` (it does not extend `AbstractCommandExecutor`), and the surrounding `catch`
lists only the four reflective checked exceptions, so the exception escapes (issue #272). Removing
this overload also removes that escaping cast, so plan 07-15's later deletion of
`AbstractCommandExecutor` does not have to reason about it.

Replacement: `registerAll(UltiToolsPlugin)` — resolves command classes as beans from the plugin's
own container and performs no cast.

Deprecated since 6.2.5 with `forRemoval = true`; the deprecation window ran its course (one minor
release, 6.2.5 → 6.3.0). Root `CLAUDE.md`'s own measurement already recorded **zero** call sites
for this overload in `src/main` (control: **1** for the single-argument form) as of Phase 4 plan
04-08, which made both `PluginManager` registration entry points resolve commands as beans instead
of package-scanning.

**What an un-recompiled downstream JAR sees.** A module calling this overload directly fails to
load with `NoSuchMethodError`, turned into one `SEVERE` `ModuleScanDiagnostics` summary per D-19;
the module still loads and enables around the gap. No currently-deployed trigger was found.

### Recorded instance: `ListenerManager`'s deprecated overloads are gone (GEN-04, 6.3.0 — `register` on the ordinary schedule, `registerAll` under same-release exception clause 2)

`manager.ListenerManager#register(UltiToolsPlugin, Listener)` (the overload taking an
already-constructed instance, performing no dependency injection) and
`registerAll(UltiToolsPlugin, String)` (the reflective package-scan overload) are both deleted.
The `Class`-taking and single-argument forms survive unchanged.

Replacement: `register(UltiToolsPlugin, Class)` for the first; `registerAll(UltiToolsPlugin)` for
the second, which additionally honours `manualRegister()` where the package-scan overload never
did (GEN-05, #337).

**`register(UltiToolsPlugin, Listener)`: ordinary schedule.** Deprecated since 6.0.5 with
`forRemoval = true`; the deprecation window ran its course.

**`registerAll(UltiToolsPlugin, String)`: same-release exception, clause 2.** This overload carries
`@Deprecated(since = "6.3.0", forRemoval = true)` — zero minor releases have passed since that
annotation first appeared. It does not qualify under clause 1 (it is not non-functional; it
successfully registers listeners, it simply never consults `manualRegister()`, which is a design
gap rather than a failure to run). It qualifies under clause 2 by the same test this document's
`aop.AopProxyBeanPostProcessor` record already applies: evaluated at removal time, this overload
has **zero** callers anywhere in `src/main` — Phase 4 plan 04-08 removed `PluginManager`'s last
in-framework caller of it (mirroring the equivalent `CommandManager` change), and the six migrated
downstream repositories and 16 pre-built module JARs show zero external references either. It
*was* wired into a real caller in the released 6.2.5 baseline (before 04-08's change, which landed
within this same unreleased 6.3.0 cycle), but by the time this plan removes it, nothing anywhere
this project can observe calls it — there is no currently-working integration for a deprecation
window to protect.

**Internal registration logic preserved under a private name.** Unlike `CommandManager`,
`ListenerManager` had no separate private helper duplicating `register(UltiToolsPlugin,
Listener)`'s actual registration body (`Bukkit`'s `registerEvents` call plus `listenerListMap`
tracking) — both surviving `register(UltiToolsPlugin, Class)` and `registerAll(UltiToolsPlugin)`
called the public deprecated overload directly for that step. Preserved verbatim under a new
private `registerListener(UltiToolsPlugin, Listener)` primitive, so both survivors behave
identically before and after this removal.

**What an un-recompiled downstream JAR sees.** A module calling either removed overload directly
fails to load with `NoSuchMethodError`, turned into one `SEVERE` `ModuleScanDiagnostics` summary
per D-19; the module still loads and enables around the gap. No currently-deployed trigger was
found for either overload.

### Recorded instance: `aop.CglibProxyFactory` is gone (6.3.0, same-release exception clause 1)

was found, and none is expected — the class never worked on this project's target platform.

### Recorded instance: `aop.ProxyFactory#createProxy(T)` / `createProxy(Class<T>, T)` are gone (6.3.0, same-release exception clause 2)

Both `createProxy` overloads on `aop.ProxyFactory` are deleted. `createProxyClass(Class<T>,
Set<Method>)` — a different method, building the proxy *class* rather than a proxy *instance* —
survives unchanged and is the framework's current mechanism.

Replacement: `aop.ProxyFactory#createProxyClass(Class<T>, Set<Method>)`, used through the
container. Proxy creation moved to *before* the bean is constructed (issue #190: a
`BeanPostProcessor` only ever sees an already-built instance, which is structurally too late for
what `AopProxyResolver` needs to do).

**Same-release exception, clause 2 (never reached a tagged release).** `aop.ProxyFactory` itself
was added after 6.2.5, within this same still-unreleased 6.3.0 development cycle (PR #305), so its
`createProxy` methods never reached a tagged release — there is no released behaviour a deprecation
window would protect. Superseded within this same cycle by `AopProxyResolver`, which resolves the
proxy class before the bean is constructed; a `BeanPostProcessor` cannot do that by interface
contract, since both of its callbacks take an already-built instance. Neither method had any
downstream reference at any point. See issue #190.

**What an un-recompiled downstream JAR sees.** No downstream JAR can reference these methods —
they never appeared in a published `UltiTools-API` artifact, so no compiled-against-6.2.5 class
file can name them. This is the same "never shipped" case `@OptionalParam`'s record documents:
there is no failure mode to describe because there is no prior binary that could have called it.

### Recorded instance: `aop.AopProxyBeanPostProcessor` is gone (6.3.0, same-release exception clause 2)

`aop.AopProxyBeanPostProcessor` is deleted in full — the whole class, including its constructor,
`addAdvisor`, `getAdvisors`, and `removeAdvisor`.

Replacement: `aop.AopProxyResolver`, consulted by the container before construction instead of
after.

**Same-release exception, clause 2 (shipped but never wired into anything that calls it).**
`AopProxyBeanPostProcessor` is older than the other two AOP entries above (`@since 6.2.0`, and it
did ship in 6.2.1 through 6.2.5), but it was never wired into the container —
`addBeanPostProcessor` had zero callers in `src/main` for its entire released history. Removing it
therefore breaks no working integration: the published 6.2.5 jar's own `AopProxyBeanPostProcessor`
is referenced only by itself, and `PluginManager` has zero references to `AopAdvisor`,
`addAdvisor`, or `TransactionInterceptor` in that release. Superseded within this cycle by
`AopProxyResolver`, for the same structural reason as `ProxyFactory#createProxy` above. See issue
#190. This is the precedent plan 07-14 later applies the identical test to for
`ListenerManager.registerAll(UltiToolsPlugin, String)` — "zero callers evaluated at removal time,"
not "never shipped."

### Recorded instance: `annotations.Propagation.NESTED` is gone (6.3.0, same-release exception clause 2 — controllability, not impossibility)

The `NESTED` constant is removed from the `Propagation` enum. The six remaining constants
(`REQUIRED`, `REQUIRES_NEW`, `SUPPORTS`, `NOT_SUPPORTED`, `MANDATORY`, `NEVER`) are exactly Jakarta
Transactions 2.0's `TxType` set.

Replacement: none direct. A savepoint-scoped nested transaction is not currently expressible
through `@Transactional`.

**Same-release exception, clause 2 — a distinct variant from the other three entries above.** All
seven original `Propagation` values, `NESTED` included, *are* implementable against the storage
layer — `NESTED` maps cleanly to `Connection.setSavepoint()`. It is dropped on **controllability,
not impossibility**: savepoint behaviour depends on whichever `sqlite-jdbc` version the server's
own Paper build happens to ship (`org.xerial:sqlite-jdbc` is not declared in this project's
`pom.xml` or `plugin.yml` — Paper supplies it — and versions `3.45.3.0`, `3.46.0.0` and `3.47.0.0`
have all been observed across local server caches), which this project can neither pin nor test
across. Clause 2's evidence, stated rather than argued: `@Transactional` has never executed in any
released version — the published 6.2.5 jar's `AopProxyBeanPostProcessor` is referenced only by
itself, and `PluginManager` has zero references to `AopAdvisor`, `addAdvisor`, or
`TransactionInterceptor` — so no released server ever evaluated `NESTED` regardless of this
reasoning. Across 17 in-house module/plugin repositories, `TransactionManager` /
`@Transactional` / `.transaction(` score **zero** hits, against a control of **94** hits for
`getDataOperator` (confirming the survey mechanism itself works). `NESTED` may be restored later if
savepoint behaviour ever becomes reliably pinnable across supported Paper builds.

summary per D-19; the module still loads and enables around the gap. No currently-deployed trigger
was found, and none could have been — no released version's `@Transactional` machinery ever
evaluated any `Propagation` value, `NESTED` included.
